# Vapi order support: answer status calls and capture callbacks

**Import one workflow. Seed two demo orders. Give a Vapi assistant two tools backed by a visible n8n callback queue.**

`getOrderStatus` checks an order number and checkout email, then returns fulfillment and tracking details. `requestCallback` checks the same pair and records the caller's number and reason for a human support team. Each tool call keeps its own ID; a batch can contain successful results and individual errors in one HTTP 200 response.

## What you get

- [`workflow.json`](workflow.json): an importable workflow with a Manual setup branch, native Data Tables, a Header Auth webhook, per-tool routing, and a single response envelope.
- [`vapi-tools.json`](vapi-tools.json): two Vapi Function tool definitions with JSON parameter schemas.
- [`fixtures/`](fixtures/): realistic tool-call HTTP bodies and a nine-scenario, stateful [acceptance contract](fixtures/acceptance.json).
- An operator-facing callback queue in **n8n → Data Tables**. Team members call the customer and update the row's `status`.

The backend uses your n8n instance's Data Tables. The voice experience uses your Vapi account, assistant, and chosen voice/model providers. The setup targets n8n **2.41.7** with Data Table node **1.1**.

## 1. Import and seed your workspace

1. Download `workflow.json`. In n8n, choose **Import from File** and open it in the project that will own the demo tables.
2. Open **Vapi webhook** and create a **Header Auth** credential:
   - **Name:** `X-Vapi-Secret`
   - **Value:** a random secret you control, for example one generated by `openssl rand -hex 32`.
3. Run the **Set up demo tables** Manual trigger. It creates these tables by name and seeds two example orders:

   | Table | Purpose |
   | --- | --- |
   | `blucca_vapi_demo_orders` | Orders available to the two tools |
   | `blucca_vapi_demo_callbacks` | Human callback queue |

   | Order number | Checkout email | Status | Tracking |
   | --- | --- | --- | --- |
   | `ORD-1001` | `alex@example.com` | `shipped` | Demo Parcel / `DEMO-1001`, estimated `2026-10-12` |
   | `ORD-1002` | `jamie@example.com` | `processing` | Empty tracking and delivery-date fields |

4. Open **Data Tables** and check the two order rows. The callback table starts empty in a fresh workspace.
5. Publish/activate the workflow. Copy the Webhook node's **Production URL**, ending in `/webhook/vapi-order-support`.

The setup branch uses named tables and upserts the demo order identities. Use the demo tables for the walkthrough; a dedicated production table keeps real order data under your own import/sync process.

## 2. Try the HTTP backend

From this repository's root in Bash, set your endpoint and Header Auth value:

```sh
export VAPI_ORDER_URL='https://YOUR_N8N_HOST/webhook/vapi-order-support'
read -r -s -p 'Header Auth value: ' VAPI_ORDER_SECRET; echo
export VAPI_ORDER_SECRET

curl --fail-with-body -sS "$VAPI_ORDER_URL" \
  -H 'Content-Type: application/json' \
  -H "X-Vapi-Secret: $VAPI_ORDER_SECRET" \
  --data-binary @examples/vapi-order-support/fixtures/two-orders.request.json
```

Expect two entries in `results`, identified by `status-A` and `status-B`. Their `result` strings contain the corresponding `ORD-1001` / `ORD-1002` data. A successful entry looks like:

```json
{
  "toolCallId": "status-A",
  "result": "{\"status\":\"found\",\"orderId\":\"ORD-1001\",\"fulfillmentStatus\":\"shipped\",\"carrier\":\"Demo Parcel\",\"trackingNumber\":\"DEMO-1001\",\"estimatedDelivery\":\"2026-10-12\"}"
}
```

Create a callback, then replay the **same request**:

```sh
for delivery in 1 2; do
  curl --fail-with-body -sS "$VAPI_ORDER_URL" \
    -H 'Content-Type: application/json' \
    -H "X-Vapi-Secret: $VAPI_ORDER_SECRET" \
    --data-binary @examples/vapi-order-support/fixtures/callback-create.request.json
  echo
done
```

Both responses should return the same callback `requestId`. Open `blucca_vapi_demo_callbacks`: one row contains the phone, reason, verified order/email pair, and `pending` status. The support team can work directly from that queue.

### Request identity and retries

The stored `requestKey` is `JSON.stringify([message.call.id, toolCall.id])`. Sequential delivery retries reuse the existing row, including a status edited by the support team. A reused key carrying changed callback details returns a tool error. A new Vapi call ID or tool-call ID identifies a fresh request.

The replay contract covers **sequential deliveries**. For concurrent duplicate delivery, use a storage integration with a unique `requestKey` constraint and an atomic insert/conflict operation. The workflow's response-building and tool correlation carry over to that implementation.

## 3. Connect the two Vapi tools

1. In Vapi, open **Settings → Integrations → Server Configuration → Add Custom Credential**.
2. Choose **Bearer Token**, set **Header Name** to `X-Vapi-Secret`, switch **Include Bearer Prefix** off, and enter the same secret saved in n8n. Save and copy the credential ID.
3. In [`vapi-tools.json`](vapi-tools.json), replace both `server.url` values with the n8n Production URL and both `server.credentialId` values with that credential ID.
4. Create two **Function** tools in Vapi's **Tools** section using the names, descriptions, and parameters in the file. Set synchronous execution, the production Server URL, and the saved custom credential. The API alternative is one `POST https://api.vapi.ai/tool` per object in the file's array.
5. Add `getOrderStatus` and `requestCallback` to your saved assistant. Keep the Server URL in the saved organization tool configuration so Vapi attaches its credential.
6. Add the behavior below to your assistant instructions, adapting the shop name and support policy.

> You help callers check orders and ask for a human callback. Ask for the order number and the email used at checkout before using either tool. Use getOrderStatus to read the recorded fulfillment status. Treat empty tracking fields as tracking details pending. If the tool returns order_not_found, ask the caller to check the order number and email. For a callback, confirm the phone number and a short reason, then use requestCallback. Once it returns callback_requested, tell the caller that the support team has received the request. Give a callback time only when the shop's supplied policy provides one. For a tool error, explain that the action needs another attempt or assistance from the support team.

7. Run a Vapi web call with the two demo order identities. Then request a callback and inspect **Vapi call log → Messages / Webhooks** together with the n8n execution and callback row. A phone-number deployment adds your chosen inbound telephony route to this same assistant.

The shipped fixtures exercise the **n8n HTTP backend and persistent table state**. Your connected Vapi web/phone call verifies speech recognition, the model's tool choice, authenticated Vapi delivery, and spoken results with your account configuration.

## 4. Bring your own orders

Prepare your order import or sync with these string columns:

| Column | Meaning |
| --- | --- |
| `orderId` | Customer-visible order number; use a stable unique value per order |
| `email` | Checkout email, normalized to lowercase |
| `status` | Fulfillment status the assistant should read |
| `carrier` | Carrier name, or an empty string |
| `trackingNumber` | Tracking reference, or an empty string |
| `estimatedDelivery` | Customer-facing delivery date/text, or an empty string |

Create a production Data Table with this schema, import a CSV or sync from your order system, and select that table in **Find matching order**. Keep it in the workflow's project. Publish the updated workflow and repeat the HTTP lookup with a known order/email pair.

The matching pair provides an **order lookup check** for this support workflow. Apply your shop's customer-verification policy before sharing higher-sensitivity data or adding order-changing tools. This template returns the listed fulfillment fields and records callback requests.

Callback rows contain `requestKey`, `orderId`, `email`, `phone`, `reason`, and `status`; n8n supplies each row's `id` and timestamps. The operations team owns the queue: contact the caller and set a status such as `contacted` or `resolved`. Connect your help desk or notification channel to that queue when your support process needs it.

## Acceptance contract

Run the scenarios in order against freshly seeded demo orders and an empty demo callback table. [`acceptance.json`](fixtures/acceptance.json) defines exact response fields, callback row values, and captured row IDs.

| Scenario | Expected behavior |
| --- | --- |
| `two-orders` | Two distinct IDs retain their corresponding order data |
| `mixed-results` | Two successful lookups survive beside an unknown-tool `error` |
| `invalid-arguments` | Missing email, string-valued arguments, and invalid callback details each return a tool error; the valid sibling succeeds |
| `unmatched-details` | Cross-customer email and unknown order return `order_not_found`; callback row count stays zero |
| `missing-call-id` | Callback returns a call-ID error; lookup still succeeds |
| `callback-create` | Lookup and callback succeed together; one matching row is stored |
| `callback-replay` | The identical request returns the original row ID and leaves one row |
| `callback-conflict` | Changed details under the same key return an error and preserve the recorded row |
| `callback-other-call` | Reusing the tool-call ID in a second Vapi call creates a separate row for the second order |

The request contract is a non-empty `message.toolCallList` with unique string call IDs, `message.type: "tool-calls"`, and object-valued `function.arguments`. Callback calls also supply `message.call.id`. Every accepted tool-call batch returns HTTP 200 and exactly one `result` or `error` single-line string per input `toolCallId`. Success values are compact serialized JSON. The suite matches IDs across the batch and checks the complete result fields. Additional endpoint checks cover the configured secret, missing/wrong authentication, and repeated Manual setup.

Verification scope: production n8n HTTP delivery, native Data Tables, response contracts, and sequential replay. The connected voice acceptance described above uses your Vapi assistant and real call trace.
